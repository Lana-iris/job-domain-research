# 岗位扫描采集规则

## 一、目的与边界
- 只负责发现候选、记录检索覆盖、核验详情页可读性。
- 不写 JD 库、不改分数、不做去重合并、不写日报。

## 二、检索位矩阵
- 来源：`research-state.md` §二。
- 列：`ID | 检索主题 | 必含词/扩展词 | 每轮最低 query 数 | 城市范围 | 平台范围 | 启用`
- `ID` 格式 `QP\d+`，稳定不变。
- 每轮默认每日一轮；未启用检索位需说明原因。
- 每个启用检索位每轮至少执行「每轮最低 query 数」；每个计划平台每轮至少 1 次检索。
- `平台范围` 为空表示使用全局平台清单。

## 三、覆盖台账
- 使用 `templates/platform-coverage.xlsx`。
- 列序：`检索日期 | 平台 | 检索位/查询词 | 城市 | 检索状态 | 相关候选数 | 入库数 | 访问限制/筛选说明 | 证据链接`
- 检索状态只允许：`已检索` / `受限` / `未执行`。
- `已检索`：查询已执行且结果页可读；候选数填实际线索数，可为 0。
- `受限`：执行了，但登录墙/详情不可访问；候选数填可见线索数或 0；必须写限制原因。
- `未执行`：计划内但没跑；候选数留空或 0；必须写未执行原因。
- 「已检索但候选数为 0」不等于「未执行」，也不等于「受限」；三者不得混用。
- 已检索但候选数为 0 时，说明写「未发现可核验结果」。
- `入库数`：扫描阶段未知时留空或填 0；O2b 完成后由 `coverage_tool.py update` 回填本次实际新增数。
- 同一 `平台 + 检索位 + 城市 + 日期` 默认只允许一行。
- 字段口径与校验以 `python3 coverage_tool.py describe` 输出为准；写入由 `coverage_tool.py append` 完成。

## 四、候选发现
- 关键词子串命中 → 进入候选池；记录对应检索位与查询词。
- 候选只代表线索，不代表合格，不得直接入库。

## 五、候选核验
- 打开岗位详情页，确认公司、职位、城市、职责与在招状态。
- JD 库的 `原文链接` 必须是岗位详情页 URL；搜索页、列表页、聚合页只作线索。
- 详情页打不开 → 记入覆盖台账「受限」，不得作为合格候选入库。
- 仅看到列表页或摘要 → 记为线索，不进入 `jd_tool.py add`。
- 核验不合格的原因写入覆盖台账的「访问限制/筛选说明」。

## 六、合规
- 使用公开索引检索；不登录、不突破登录墙、不存个人数据。
- 登录墙平台标「需用户手动补充」，不得伪装为已扫描。

## 七、平台清单
- 覆盖：LinkedIn 领英 / 猎聘 Liepin / Indeed / 智联招聘 / 前程无忧 51job / 拉勾 / 各公司官网 careers 页。
- 需用户手动补充：脉脉（登录墙）、Glassdoor（登录墙）、BOSS 直聘（索引滞后，仅用户主动粘贴时作为用户补充线索交给 O2b）。
- 发现新平台及时补充。

## 八、交接输出
- `platform-coverage.xlsx`：本轮检索覆盖证据。
- 覆盖不足时，报告检索平台与查询范围（对应台账中 `受限` / `未执行` 的行）。
- 合格候选：进入 O2b 的 `add` / `refresh` 输入。
- 不合格候选：只在覆盖台账说明中记录，不单独建文件。
- 0 新增时，O1 需三态归因：检索失败（未执行/受限）/ 有候选但全部去重或核验淘汰 / 无候选。扫描提供覆盖状态与候选数；O2b 提供去重与淘汰计数。
